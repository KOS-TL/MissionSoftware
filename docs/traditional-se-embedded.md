## 0. 立场：纳入，而非替换

传统软件工程以**需求 → 设计 → 实现 → 测试**（及发布/运维）组织系统交付。  
使命软件工程**不另起一条与之平行的生命周期**，而是假定上述流程仍完整存在，并在每一段强制增加可机检约束：

> **明示托付 ∧ 当前动作仍对准该托付 ∧ 判定可被证伪**

本示例（Microkit 两保护域：`gatekeeper` + `client`）过去容易被看成「只有实现尖刺」。下文把传统四段**全部写进同一示例**，使每一段都有对应产物、验收口径与使命叠加项。  
圆心仍是：防止把「跑通 / 测试绿 / 内核强」误当成「人托付的那件事现在仍在被正确地做」。

## 2. 需求工程（Requirements）——写入本示例

### 2.1 传统需求对象（本示例已具备的「功能规格」）

在 Microkit `qemu_virt_aarch64` 上构建最小用户态系统，包含：

1. 被动保护域 **gatekeeper**：经 PPC 接收请求并返回允许/拒绝/共签状态/证据 tip。  
2. 主动保护域 **client**：按场景脚本发起请求序列。  
3. 构建与运行：容器内交叉编译 + QEMU；超时收尾可接受（`rc=124`）。

### 2.2 使命叠加后的需求（必须写成需求，不能只写在理念里）

**R1 明示托付（人侧通道）**

- 系统启动后，人共签状态默认为 **OFF**。  
- 未 GRANT 前，任何「合法仿真」类请求必须 **DENY**，原因码含 `no_human_cosign`。  
- GRANT / REVOKE / QUERY 必须经显式消息，禁止静默共签。  
- 本示例中的共签为**演示占位**，需求层面明确：**不等于**电子签名/法规共签系统。

**R2 仍在执行被托付的一件（对准与禁区）**

在共签 **ON** 之后，下列请求仍必须 **DENY**（假使命需求，不是可选）：

| 需求 ID | 场景 | 期望 |
|---|---|---|
| R2.1 | `expired_trust` | `DENY\|expired_entrustment` |
| R2.2 | `forbidden_zone` | `DENY\|forbidden_zone` |
| R2.3 | `advisor_enable` | `DENY\|advisor_cannot_enable` |
| R2.4 | `empty_u_achieve` | `DENY\|empty_U_no_achieve_tag` |

**R3 合法路径的弱成功语义**

- 共签 ON 且对准托付时，可返回 `ALLOW_SIM`。  
- 需求强制附带语义：`sim_only`；**delivery ≠ achievement**；**非临床**。  
- 禁止把 `ALLOW_SIM` 在需求/验收中表述为「使命达成」。

**R4 检查可证伪（证据）**

- 每次关键判定写入证据事件；演示级 FNV-1a32 链（`prev`/`this`/`seq`）。  
- 可查询 tip 与长度；`full` 剖面期望 `len=10` 且 tip 与末事件一致。  
- 需求声明：该链为**教学用顺序联结**，不作密码学抗碰撞保证。

**R5 非目标（Negative requirements，传统 SE 常缺、本示例必写）**

- 不出束、无厂商写使能、无注册材料。  
- 不重做 seL4 证明；不宣称应用级 seL4/CompCert 保证。  
- 不实现真实临床剂量/联锁业务逻辑（本示例是约束外壳，不是 MRTDS 成品）。

### 2.3 需求可追溯

每个 R* 在实现中对应协议常量与日志关键词；在测试中对应 `DEMO_PROFILE` 场景步。  
传统「需求追溯矩阵」在本示例中的最小形态：

| 需求 | 实现锚点 | 测试锚点（串口） |
|---|---|---|
| R1 | 共签状态机；GRANT/REVOKE/QUERY | `COSIGN\|STATE=OFF/ON`；`DENY\|no_human_cosign` |
| R2.* | 假使命判定分支 | 四条 `DENY\|…` |
| R3 | `ALLOW_SIM` + `GATE\|NOTE\|sim_only…` | `ALLOW_SIM` 且非「达成」表述 |
| R4 | 证据链；`REQ_EVIDENCE_TIP` | `EVIDENCE\|seq=`；`CHAIN\|tip=…\|len=10` |
| R5 | 文档与答辩口径；无写使能接口 | 工程中不存在出束/写使能路径 |

## 3. 设计（Design）——写入本示例

### 3.1 传统设计对象

- **静态结构**：`mission.system` 声明两 PD、通道与权限；board=`qemu_virt_aarch64`，config=`debug`。  
- **动态交互**：client 发起请求 → gatekeeper（passive）经 PPC 应答。  
- **构建设计**：宿主机 Docker 挂载 `microkit_work`，SDK 在 `/work/microkit-sdk-2.3.1`。

### 3.2 使命叠加后的设计决策（设计说明书应写明的「为何如此」）

**D1 分层职责（K/A/M/U）**

| 层 | 本示例含义 | 设计含义 |
|---|---|---|
| K | 引用 seL4/Microkit | 底座能力，不自动导出「应用使命达成」 |
| A | gatekeeper/client 演示代码 | 条件保证范围P的主体 |
| M | 共签·禁区·证据纪律 | 行为纪律，必须可测 |
| U | 真签、真硬件、临床、密码学强度链等 | 显式未覆盖，禁止偷渡为「已达成」 |

**D2 人审判在架构上的位置**

- 共签是**显式状态机**，默认 OFF，而不是配置文件里的隐式 true。  
- 设计禁止：启动即视为已托付；模型/顾问路径直达使能。

**D3 成功语义分层**

- 设计上区分三类结果：`DENY` / `ALLOW_SIM` /（本示例不提供的）`ACHIEVE`。  
- 不设置「达成」成功码，是为从设计上阻断「绿 = 达成」。

**D4 证据设计**

- 事件追加写；`this = H(prev ∥ event)` 的演示级联结；对外提供 tip 查询。  
- 设计目标是**可对质的顺序痕迹**，不是安全审计产品。

**D5 场景可切换（测试性设计）**

- `DEMO_PROFILE`：`full` | `cosign_only` | `false_only` → 不同 client 目标文件。  
- 使需求 R1–R4 可在设计层被「剖面」覆盖，而非手工改代码才能测。

### 3.3 设计视图（答辩可用的一句话结构）

> 传统 SE 的「组件图 + 时序图」在本示例中就是：Microkit 两 PD + 共签/判定/证据三条时序；使命工程要求这三条时序在设计阶段就不可删除。

## 4. 实现（Implementation）——写入本示例

### 4.1 传统实现对象

| 文件/产物 | 传统角色 |
|---|---|
| `gatekeeper.c` | 服务端/策略实现 |
| `client.c` / `scenarios/client_*.c` | 驱动/场景客户端 |
| `mission_proto.h` | 接口与消息约定 |
| `mission.system` | 系统组装（类部署描述） |
| `docker_build_run.sh` | 构建与运行脚本 |
| `build/loader.img` | 可加载产物 |

实现活动包括：交叉编译、链接 `-lmicrokit`、`microkit` 工具生成 loader、QEMU 启动。

### 4.2 使命叠加后的实现纪律（编码时必须遵守）

1. **默认拒绝共签**：初始化 `human_cosign_ok = 0`（或等价）。  
2. **先判共签与对准，再谈业务**：本示例无真实业务，因此「业务」退化为场景标签；但顺序不可颠倒。  
3. **日志即契约**：关键路径必须打出稳定关键词，供测试与答辩指认（见需求追溯表）。  
4. **弱成功必须标注**：`ALLOW_SIM` 必伴随 `sim_only; delivery!=achievement; non-clinical`。  
5. **不实现写使能**：实现范围刻意不含出束/设备写接口（落实 R5）。

### 4.3 实现与「仍在被正确地做」的对应

软件表达「人托付的那件事现在仍在被正确地做」在本示例实现中的合取式：

```
有效明示托付（共签 ON 且未撤销）
∧ 当前请求通过禁区/过期/妄图使能/空U达成 等对准检查
∧ 判定已写入可查询证据链
```

任一为假 → 不得以「功能返回成功」代替；本示例用 `DENY` 或仅 `ALLOW_SIM`（弱）表达。

## 5. 测试（Verification & Validation）——写入本示例

### 5.1 传统测试在本示例中的位置

| 测试类型 | 本示例做法 |
|---|---|
| 构建冒烟 | Docker 内编译通过，生成 `loader.img` |
| 系统集成 | QEMU 启动至用户态，Monitor/PD 起来 |
| 场景/验收测试 | `DEMO_PROFILE=full` 固定请求序列 |
| 回归 | 同一命令复跑；对照跑通记录 |
| 负面测试 | 假使命四条 + 共签前/撤销后合法请求 |

S0（`sel4test`）属于**工具链与底座冒烟**，不计入本示例对「应用使命」的 V&V；但纳入课题生命周期的「环境就绪」门禁。

### 5.2 使命叠加后的测试用例（必须全部失败或全部按预期拒绝）

**验收命令（唯一推荐）：**

```bat
docker run --rm -e DEMO_PROFILE=full -v <REPO_ROOT>:/work -w /work/mission-shell trustworthysystems/sel4:latest bash /work/mission-shell/docker_build_run.sh
```

**`full` 剖面期望序列（传统「测试步骤 + 期望结果」）：**

1. `COSIGN STATE=OFF`  
2. `legal_before_cosign` → `DENY|no_human_cosign`  
3. `cosign_grant` → `GRANT`；再查 `STATE=ON`  
4. `legal_sim` → `ALLOW_SIM` + `sim_only` 注释  
5. 四条假使命 → 全部 `DENY`（对应 R2.1–R2.4）  
6. `cosign_revoke` → `REVOKE`  
7. `legal_after_revoke` → 再次 `DENY|no_human_cosign`  
8. `evidence_tip` → `tip=…|len=10`  
9. `MISSION_SHELL_DEMO_DONE`  
10. QEMU `rc=124`（timeout）可接受，**不以进程退出码 0 为成功判据**

### 5.3 传统「通过准则」如何被改写

| 若只按传统习惯 | 本示例的通过准则 |
|---|---|
| 编译过、QEMU 起来、有一条绿灯 | 必须出现完整 DENY/GRANT/REVOKE/链 tip 序列 |
| 退出码 0 | 关键词契约 + 证据 tip/len；timeout 可接受 |
| 「功能测过了」 | **负面用例必须测到拒绝**；否则纪律未测 |

这就是传统测试被「完全纳入」后的形态：测试计划仍在，通过准则增加使命可证伪条款。

## 6. 发布、复现与运维（传统生命周期后半段）

本示例如本科毕设演示系统，对应传统「发布/运维」的最小纳入：

1. **可复现交付物**：源码树、Docker 命令、跑通记录（v3）、开题报告、答辩 PPT。  
2. **配置管理**：`DEMO_PROFILE` 作为受控配置；无 profile 的旧日志**不得**当作现行验收。  
3. **演示运维脚本**：现场只跑 `full`；口述时按「托付→人审判→禁区→证据」指日志。  
4. **事件响应**：若 tip/len 不符或假使命变 ALLOW，视为发布失败，而非「差不多绿了」。

## 7. 一条故事线：同一示例走完传统全流程

可用下面这条答辩/写作叙事，证明「传统 SE 已完全在场」：

1. **需求**：写出 R1–R5（托付、对准、弱成功、证据、非目标）。

缺任一段，示例就退回「只有实现尖刺」；四段齐全时，它才是**嵌在完整软件工程流程中的使命约束外壳**，而不是悬空的理念口号。

## 9. 结论

将传统软件工程**完全纳入**本示例，含义是：

- 不是把 Microkit 尖刺单独称为「新学科替代生命周期」；  
- 而是让**同一示例**同时具有需求规格、设计决策、实现产物、测试与复现门禁；  
- 并在每一段叠加「托付—对准—可证伪」；  
- 从而使「人托付的那件事现在仍在被正确地做」成为**有生命周期载体的工程命题**，而不是实现日志里的几行 DENY。

**一句话收束：**  
传统软件工程提供把系统做出来的全流程；本示例证明该流程可以、也必须承载使命纪律——`DEMO_PROFILE=full` 是测试段的尖峰，R1–R5 与 D1–D5 则表明尖峰前后需求与设计从未缺席。
